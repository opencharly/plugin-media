# 2026.250.1633 — fix(media): the transcode word scales odd-dimension sources to even (libx264)

## Summary

The "transcode: {to: mp4}" pipeline word hard-failed its ffmpeg run whenever the
source MJPEG carries odd frame dimensions — libx264 rejects "height not divisible
by 2". The Cutover E-3 R10 bed (the chrome-headless fixture CDP screencast
session) exposed it live: the E-3 recorder's Page.startScreencast frames
measured 780x437 (odd height, the browser's default headless viewport), so the
bed's evidence phase died with:

    ffmpeg transcode failed: [libx264] height not divisible by 2 (780x437) ...

The transcode verb is the shared post-capture pipeline for EVERY catalog session
verb (spice/vnc/libvirt/cdp/adb/appium), so any verb whose capture device reports
odd dimensions hits the same wall. No capture plugin can guarantee even dims.

## Change

runTranscode's ffmpeg argv gains a scale filter to the nearest even
dimensions, preserving the h264/yuv420p output contract:

    ffmpeg -y -loglevel error -i <mjpeg> -vf scale=trunc(iw/2)*2:trunc(ih/2)*2 -c:v libx264 -pix_fmt yuv420p <out>

trunc (never ceil) keeps a 1px dimension from wrapping negative; the aspect
ratio is preserved (the same factor applies to both axes).
