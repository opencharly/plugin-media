# 2026.250.1643 — fix(media): scale odd-dimension sources to even in the transcode word (#2)

## Summary

The `transcode: {to: mp4}` pipeline word hard-fails its ffmpeg run whenever the source MJPEG carries odd frame dimensions — libx264 rejects "height not divisible by 2". The **Cutover E-3 R10 bed** (chrome-headless fixture CDP screencast session, plan nested-capture-architecture §Cutover E unit 3) exposed it live: the E-3 recorder's `Page.startScreencast` frames measured **780x437** (odd height — the browser's default headless viewport), so the bed's evidence phase died at the mp4 step. The transcode verb is the shared post-capture pipeline for EVERY catalog session verb (spice/vnc/libvirt/cdp/adb/appium), so any capture device reporting odd dimensions hits the same wall — no capture plugin can guarantee even dims.

`runTranscode`'s ffmpeg argv gains a scale filter to the nearest even dimensions, preserving the h264/yuv420p contract:

```
ffmpeg -y -loglevel error -i <mjpeg> -vf scale=trunc(iw/2)*2:trunc(ih/2)*2 -c:v libx264 -pix_fmt yuv420p <out>
```

`trunc` (never ceil) keeps a 1px dimension from wrapping negative; aspect ratio preserved.
