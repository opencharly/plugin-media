# 2026.251.1349 — fix(media): transcode pins the output video track timescale — tolerate the Appium screenrecord invalid-duration MP4 (E-5)

## Summary

The E-5 check-android-emulator-pod evidence phase failed on run 2026.251.1258 — every bed phase green (check-live 302/0), the pulled Appium MP4 valid per ffprobe (h264 160.6s, 82.8MB) — yet the transcode pipeline word died:

```
ffmpeg transcode failed: [mp4 @ 0x5603a4254440] Application provided duration: 3469067760 in stream 0 is invalid
[vost#0:0/libx264 @ 0x5603a4254840] Error submitting a packet to the muxer: Invalid argument
Task finished with error code: -22 (Invalid argument)
```

**RCA:** the Appium stopRecordingScreen MP4 declares a 90000-Hz video track (`r_frame_rate=90000/1`, `time_base 1/90000`) with non-monotonic dts; the mp4 muxer derives the OUTPUT duration from the last dts at the source timescale and that computation overflows its validity check → mux error -22 (exit 234).

**Fix:** the transcode invocation now pins the output video track timescale (`-video_track_timescale 1000`) — the muxer's duration computation stays in range for ANY source. The MJPEG path is unaffected (the flag only fixes the output track timescale; the normal path's end-to-end test passes with the flag).

Reproduced live on the actual pulled MP4 (run 1258 media/appium-1.mp4):
- plain invocation → `exit=234`, the `Application provided duration: 3469067760` mux error
- with the pin → `exit=0`, valid output (ffprobe duration=160.605000, h264 mp4)
